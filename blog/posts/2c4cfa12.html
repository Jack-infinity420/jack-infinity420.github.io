网络流量入门（四）：Wireshark 动手实验与自测

2026-11-17 · tech / 流量分析 · 约 4596 字 · 阅读约 12 分钟

网络流量入门（五篇）：零·导览 ｜ 一·从比特到流 ｜ 二·92 个特征 ｜ 三·从端口法到 nDPI ｜ 四·动手实验

前三课是”看”，这一课是”做”。所有实验都用 demo_handshake.pcap（我为你专门构造的 27 个包的抓包， 里面故意包含了：DNS、TCP 握手、TLS 1.3 ClientHello 带 SNI、加密应用数据、RST、SSDP、mDNS、ICMP、类 QUIC 的 UDP）。

为什么要用构造的抓包：真实抓包里有几千条流，你找不到”那个关键包”。 这 27 个包每一个都有教学目的，你顺着 1→27 看一遍，等于把前三课复习一遍。

注意：这个抓包里的 TLS 密码套件是随便写的、密钥是随机的，所以 Wireshark 会显示”无法解密”—— 这正是我们要的现象（加密流量就是这样）。但 SNI、握手结构、包长、时序全部真实可读。

0. 环境准备

  1. 安装 Wireshark（官网 wireshark.org，装的时候勾上 Npcap）。
  2. 打开 demo_handshake.pcap。
  3. 记住三个快捷键：
    • Ctrl+F 查找（可以按”字符串”搜载荷）
    • 右键包 → Follow → TCP Stream（看重排后的字节流）
    • 菜单 Statistics → Conversations（看”流”的视角）

建议的窗口布局：上面包列表、中间协议树、下面十六进制。永远同时看这三块—— 只看包列表会让你以为”流量就是一串 IP”，只看十六进制会让你迷失在字节里。

实验 1：验证”最小帧 60 字节”和”三层封装”

操作

  1. 过滤器输入：frame.len == 60 回车。
  2. 选中任意一个 60 字节的包（比如第 5 号）。
  3. 在中间协议树里展开 Ethernet II → Internet Protocol Version 4 → Transmission Control Protocol。
  4. 看每一层的头长度。

你应该看到

Frame           60 bytes                     ← 整帧（不含 FCS）
  Ethernet II   14 bytes                     ← 目的MAC(6)+源MAC(6)+Type(2)
    Internet Protocol Version 4  20 bytes     ← IP 头
      Transmission Control Protocol 20 bytes  ← TCP 头（纯 ACK，无选项）
      [TCP segment of ...] 0 bytes 载荷       ← 没有数据

14 + 20 + 20 = 54，但帧是 60 —— 差 6 字节是以太网最小帧补零（第一课 §1.1）。

进阶：再过滤 frame.len == 74，看 SYN 包的 TCP 选项（Options: (20 bytes)：MSS、SACK permitted、Timestamps、NOP、Window scale）。 这就是”为什么 SYN 比 ACK 大”的答案。

思考：如果这个抓包是在 Linux any 接口上抓的（SLL 头 16 字节），这些数字会变成多少？ （答案：全部 +2，因为 SLL 16 字节比以太网 14 字节多 2 字节。）

实验 2：看三次握手，并测出 RTT

操作

  1. 过滤器：tcp.flags.syn == 1 || (ip.addr == 203.0.113.10 && tcp.port == 51423)
  2. 选中第 3 号包（SYN），看 Sequence Number (raw)。
  3. 选中第 4 号包（SYN-ACK），看 Acknowledgment number。
  4. 看第 3、4 号包之间的时间差（Wireshark 的 Time 列）。

你应该看到

#3  SEQ=1000,      Flags=SYN
#4  SEQ=5000, ACK=1001, Flags=SYN,ACK      ← ACK = 对方 SEQ + 1
#5  SEQ=1001, ACK=5001,  Flags=ACK

ACK = SEQ + 1：SYN 本身占一个序号（虽然它不携带数据），这是 TCP 的规矩（RFC 9293）。

时间差：#4.Time − #3.Time = 0.041 − 0.031 = 0.010 s = 10 ms → 这就是这一跳的 RTT。 这是加密流量里唯一能直接测 RTT 的地方（握手之后全是密文，你只能靠 ACK 时序推测）。

思考：为什么 syn_packets 在 CSV 里通常是 2 而不是 1？ （答案：SYN 和 SYN-ACK 都置 SYN 标志位，计数的是包不是连接。）

实验 3：找到 SNI —— 加密世界里最后一句话（最重要）

方法 A：用过滤器

tls.handshake.extensions_server_name

方法 B：用界面

  1. 选中第 6 号包（319 字节）。
  2. 展开 Transport Layer Security → TLSv1.3 Record Layer: Handshake Protocol: Client Hello → Handshake Protocol: Client Hello → Extension: server_name (len=21) → Server Name Indication extension → Server Name: mmg.whatsapp.net

方法 C：暴力搜字节

菜单 Ctrl+F → 选 “String” → 输入 whatsapp → 查找。 你会落在第 6 号包的载荷里——因为 SNI 是明文，字符串直接躺在那里。

你应该记住的一句话

SNI 是 TLS 1.3 之后唯一稳定残留的”我要访问谁”。 它不是”加密的副产品”，而是协议本身必须明文传输的（服务器要在解密之前知道该出示哪张证书）。

思考：如果你把这个 ClientHello 加密了会怎样？ （答案：服务器不知道该给哪张证书 → 必须先用默认证书再进行 SNI 内层握手，这就是 ECH（Encrypted ClientHello） 要解决的问题；也是为什么 ECH 一旦普及，整个”SNI 指纹”体系会失效。）

实验 4：看清”加密的边界”在哪一行

操作：按顺序点第 6、8、10、11 号包，只看中间协议树的最后一行：

包号协议树最后一行你能读到什么
6Handshake Protocol: Client Hello + 全部扩展几乎全部可读（SNI、密码套件、ALPN、公钥）
8Handshake Protocol: Server Hello版本、选中的密码套件、服务端公钥共享
10TLSv1.3 Record Layer: Application Data Protocol: Hypertext Transfer Protocol只有 5 字节记录头 + 一堆密文
11同上同上

关键观察：第 10、11 号包的 Encrypted Application Data 长度是 1375/1445 字节—— Wireshark 能告诉你”有多少密文”，但完全不知道里面是什么。

这正好解释了第三课的分层：

  • 你看到的元数据（长度、时序、方向）= 0.5 层以上的信息；
  • 你看不到的载荷 = 只有拿到密钥（SSLKEYLOGFILE）才能解。

动手加分项：给 Wireshark 配置 SSLKEYLOGFILE 环境变量，再用浏览器访问一个 HTTPS 站点抓包， 就能看到解密后的 HTTP/2。这会让”加密边界”这个概念彻底变成直觉。 配置方法：Edit → Preferences → Protocols → TLS → (Pre)-Master-Secret log filename。

实验 5：RST 和 FIN 的区别

操作

  • 过滤器 tcp.flags.reset == 1 → 你会看到第 23 号包（那个被拒绝的连接）。
  • 过滤器 tcp.flags.fin == 1 → 你会看到第 16、17 号包（正常关闭）。

对比

第 16/17 号（FIN）第 23 号（RST）
后续还有 ACK 收尾（四次挥手）直接结束，没有后续
Sequence/Ack有意义Wireshark 标注 RST 后忽略
含义“我说完了”“立即断”

为什么这很重要：你数据里 14.9% 的流带 RST，其中 Reddit 的中位 RST 数是 2。 打开 reddit.csv 过滤 bidirectional_rst_packets >= 2，你会发现这些流的 dst_ip 高度集中在 gql-fed.reddit.com / w3-reporting.reddit.com 这类主机上——客户端发个请求就主动放弃。 这就是”行为指纹”诞生的地方。

实验 6：背景噪声长什么样

操作

  1. 过滤器 udp.port == 1900 → 第 24 号包。展开载荷，你会看到纯文本： 
    M-SEARCH * HTTP/1.1
HOST: 239.255.255.250:1900
MAN: "ssdp:discover"
...
  2. 看它的目的 IP：239.255.255.250 → 这是一个组播地址（224.0.0.0/4），不是公网单播。
  3. 过滤器 udp.port == 5353 → 第 25 号包，mDNS 查询 _spotify-connect._tcp.local。

这两个包和”用户在用哪个 App”有关系吗？ 没有。 手机的 UPnP/mDNS 发现服务每隔几十秒就广播一次，跟你正在刷抖音还是发微信完全无关。

这就是你数据里 39.2%“背景流量”的真身：

协议端口你数据里的流数单包占比
SSDP19005,753高（1,335 条单包流）
mDNS53531,643高
私有发现20002787全部单包（330 字节）

如果你不做这一步过滤，你的分类器有 39% 的训练样本标签是错的。 这是本数据集上”准确率只有 0.47”的头号原因，比”加密”这个理由重要得多。

实验 7：用 Wireshark 的”流”视角（统计而非逐包）

操作

  1. 菜单 Statistics → Conversations → 切到 TCP 标签。
  2. 你会看到 2 行（两个 TCP 连接），每行有 Packets / Bytes / Duration / Packets A→B / B→A。

对照你的 CSV：这一行就是 NFStream 输出的一行。把 Wireshark 的列名和 CSV 的列名对上：

Wireshark Conversations 列你的 CSV 列
Packetsbidirectional_packets
Bytesbidirectional_bytes
Durationbidirectional_duration_ms
Packets A→Bsrc2dst_packets
Packets B→Adst2src_packets
Bits/s可由 bytes/duration 算

再试：Statistics → Flow Graph（看时序图）、Statistics → I/O Graph（看速率曲线）。 你会直观看到”流量的时间形状”：突然一串、然后长时间静默——这就是第一课说的”突发性”。

实验 9：命令行版（tshark）——把实验变成脚本

GUI 适合理解，命令行适合批量。安装 Wireshark 后 tshark 在安装目录（通常 C:\Program Files\Wireshark\tshark.exe，需自行加入 PATH）。

$pcap = "demo_handshake.pcap"

# 1) 概览：每个包的编号/时间/长度/协议
tshark -r $pcap -T fields -e frame.number -e frame.time_relative -e frame.len -e _ws.col.Protocol

# 2) 只列 TLS 握手，并打印 SNI
tshark -r $pcap -Y "tls.handshake.type==1" -T fields -e frame.number -e tls.handshake.extensions_server_name

# 3) 列出所有 TCP 连接（类似 Conversations 面板）
tshark -r $pcap -q -z conv,tcp

# 4) 协议分层统计
tshark -r $pcap -q -z io,phs

# 5) 暴力搜字符串
tshark -r $pcap -Y 'frame contains "whatsapp"' -T fields -e frame.number

# 6) 每一列的完整值（学习字段名的最好办法）
tshark -r $pcap -Y "tls.handshake.type==1" -V | Select-String -Pattern "Server Name|Cipher Suite|Extension"

tshark 的 -Y 是显示过滤器（和 Wireshark GUI 里一样），-z 是统计。 想做批量分析，-T fields -e <字段> 是关键——它把抓包直接变成 CSV。

实验 10：用 pandas 复现第二课的所有统计（对你自己的 CSV）

print(df.bidirectional_packets.describe(percentiles=[.5,.9,.99]))

print(df.bidirectional_max_ps.value_counts().head(10))

答案与解析

1. 60 字节（不含 FCS 的 64）。原因：14（以太网）+ 20（IP）+ 20（TCP）= 54，不足以太网最小帧 60，补零到 60。早期以太网靠 CSMA/CD 检测冲突，必须保证最短帧发送时间 ≥ 往返传播时延。

2. MSS = MTU − IP 头 − TCP 头 = 1500 − 20 − 20 = 1460。若 MTU = 9000，则 MSS = 8960（IPv4/TCP 无选项时）。MSS 在 SYN 的选项里协商。

3. SYN 要在选项里协商 MSS、SACK、时间戳、窗口扩大，这些选项约 20 字节 → TCP 头 40 字节 → 帧 74 字节。

4. ACK 字段 = “我期望收到的下一个字节的序号”，即”前面全部收到”。ACK = 对方SEQ + 对方载荷长度 正确（SYN/FIN 各额外占 1 个序号）。

5. SYN 重传（丢包或对端无响应）。注意一次正常握手产生 2 个 SYN 位包（SYN + SYN-ACK），所以 3 个 = 2 次正常 + 1 次重传。

6. FIN = 有序关闭（走完四次挥手）；RST = 强制中止。分开统计因为：FIN 表示”正常结束”（业务完成），RST 表示”异常/放弃/被拒绝”（业务失败或客户端风格）。你数据里 Reddit 的中位 RST = 2 就是客户端主动放弃的风格。

7. flow 是观测者按”五元组 + 时间窗”切出来的统计单元；connection 是TCP 状态机意义上的连接。两个情形：① 长连接空闲超过 idle timeout（120 s）→ 被切成两条流；② active timeout（1800 s）到期强制切流；③ UDP 没有 connection 但有 flow。

8. ① 单包 DNS 查询；② 发出 SYN 但没有任何回应的半开连接（你数据里 24% 的流有 SYN、只有 20.4% 有 FIN，差额就是这类）；③ 单包 SSDP/mDNS 广播；④ 单包的 ICMP/IGMP。

9. 因为 idle timeout 被设成 120 s。工具在 120 s 没有新包时就结束这条流，所以”流内最大空档”永远不可能超过 120 s。这是工具参数，不是网络属性。

10. 因为 active timeout 被设成 1800 s（30 分钟）。同理，这是人为上限。

11. pps = packets / (duration_s + ε)，duration=0 时分母趋近 ε，pps 会爆炸到 1e11 量级。处理：① 用 log1p；② 显式截断（如 clip 到 p99）；③ 改用 packets 原始计数让模型自己学；④ 加一个 is_instant 二值特征。

12. 因为流量是重尾分布（1 GB 的那条流会把均值拉飞）。中位数描述”典型值”，均值描述”总量分摊”，两者回答不同问题。你数据里包数中位数 4、均值远大于 4。

13. bytes_per_pkt = bytes/packets ≈ 平均包长。文本/信令是小包（200–300 字节），图片/视频是接近 MTU 的包（400–520 字节）。这个量直接由内容类型决定，不受采集环境影响，所以很稳健。

14. syn_ratio = syn_packets / packets 高说明”这条流里建连动作占比高”→ 大量短连接。TikTok（0.059）和 WhatsApp（0.061）最高，因为它们有大量”发一个请求就断”的短连接。

15. 意味着”超过一半的流里，PSH 计数是 0”（这些流太小，没进入数据交互阶段）。不意味着”这个 App 不用 PSH”。facebook/instagram/youtube 的 psh_ratio 中位为 0 就是这个原因。

16. 因为 OUI 是设备厂商的标识（MAC 前 3 字节），它和”App”没有因果关系；它只在”某些设备恰好只被用来测某个 App”时才和标签相关。检测方法：把设备当分组做 GroupKFold 留出。实测：IID 0.729 → 设备留出 0.436。另一个检测法：看”某个 OUI 是否只对应一个标签且样本量大”（f8:e4:3b 的 2,011 条流 100% 是 whatsapp）。

17. 含。判断方法：看 max_ps 的最大值。你的数据是 1514，而 IPv4 的最大包长是 1500 —— 多出来的 14 正是以太网头。如果 ps 只算 IP 层，最大值会是 1500（或 1497 这种扣掉选项的值）。

18. 2000 年前后够用（应用少、端口约定严格）。失效原因：HTTP 隧道化、P2P 随机端口、移动 App 全部走 443、CDN 复用。文献：Moore & Papagiannaki, PAM 2005；Karagiannis et al., BLINC, SIGCOMM 2005。

19. ① 加密（载荷是密文）；② 规避（分片/重叠/乱序让检测器与主机看到不同字节，Ptacek & Newsham 1998）；③ 状态成本（流重组 + 百万级流表）。

20. 因为它不是纯 DPI，而是多证据融合：端口提示 → 载荷/结构解析（ClientHello、SNI、证书）→ 主机名库匹配 → IP 缓存匹配。它承认”看不到载荷就降级用旁路证据”，而不是死磕载荷。

21. master_protocol = TLS（承载协议），app_protocol = WhatsApp（在 TLS 之上识别出的应用）。nDPI 的输出是两级结构。

22. 语义是”这个结论是怎么得出的”——枚举值对应不同的证据强度（内容解析 > 缓存 > 端口 > IP > IP+端口 > 未知）。之所以要查头文件：这个枚举的整数编码在不同版本间变过，凭记忆解释一定会错。

23. 不能。JA4 描述的是 TLS 实现（库/版本/扩展顺序），不是应用。实测：主流 JA4 t13d1516h2_... 覆盖 10/10 个 App，纯度只有 0.51；只有 App 自带 TLS 栈的指纹（如 t12d1210h2_...）纯度才是 1.00。

24. 因为 nDPI 在 TLS 上能做的最强判据就是 SNI（TLS1.3 之后证书已加密）。当你已经有了 SNI，“读 SNI”和”nDPI 读 SNI”是同一件事，所以增益只有 1 个百分点。再加上你数据里 91.5% 的流共享同一个 confidence 取值，说明 nDPI 的判定几乎全部来自同一种（较弱的）证据。

学习路径：接下来学什么

你现在的水平：理解包/流/特征/nDPI 的分工
        │
        ├── 想做取证（"这台手机在用什么 App"）
        │     → 第 4 课实验 6（背景过滤）+ 08 课 §7.3 的分层
        │     → 读：RFC 8446 §4.1.2（ClientHello），Snort/Suricata 规则语法
        │
        ├── 想做机器学习分类
        │     → 读：Nguyen & Armitage 综述（2008）；本仓库 02 号报告的消融实验
        │     → 关键：先解决标签噪声，再换模型（顺序反了永远做不好）
        │
        ├── 想做高速采集/生产系统
        │     → 读：nDPI 源码（ntop/nDPI）、PF_RING、NFStream 文档
        │     → 关键：流表内存、超时策略、多线程
        │
        └── 想做隐私/反指纹（红队视角）
              → 读：ECH 草案、TLS 指纹随机化（curl-impersonate 反向思路）
              → 关键：SNI 加密 + 包长填充 + 时序扰动

推荐阅读顺序（由易到难）

  1. Kurose & Ross《Computer Networking: A Top-Down Approach》 第 3 章（传输层）、第 8 章（安全）——建立”为什么这样设计”的直觉。
  2. Stevens《TCP/IP Illustrated》Vol.1 第 17–24 章——TCP 逐字段，当字典查。
  3. RFC 8446（TLS 1.3） §4.1——ClientHello 的权威定义，比任何教程都准。
  4. RFC 7011（IPFIX） §2——“流”的工业标准定义。
  5. Deri et al., nDPI (ISWCS 2014) + nDPI 源码 src/lib/protocols/——看真实的检测器怎么写。
  6. Karagiannis et al., BLINC (SIGCOMM 2005)——不看载荷怎么分类，思路最开阔的一篇。
  7. Paxson & Floyd (ToN 1995)——流量的统计性质，理解”重尾”的源头。

最后：三条可迁移的思维方式

  1. 先问”这个数字是谁算的”（工具参数 vs 网络属性）。 你数据里 120 s / 1800 s / 1514 / 60 这四个数，前两个是工具，后两个是协议。
  2. 先问”这个字段合法吗”（requested_server_name 里躺着 5,752 个组播 IP）。 字段名是文档的承诺，字段值是现实的回答，永远以值为准。
  3. 先问”这个特征能被什么解释”（设备？时间？文件名？）。 能被非目标任务解释的特征，就是捷径，就是你在自欺欺人。
