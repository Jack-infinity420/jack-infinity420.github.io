网络流量入门（三）：从端口法到 nDPI

2026-11-17 · tech / 流量分析 · 约 4022 字 · 阅读约 11 分钟

网络流量入门（五篇）：零·导览 ｜ 一·从比特到流 ｜ 二·92 个特征 ｜ 三·从端口法到 nDPI ｜ 四·动手实验

前两课解决”有什么可看”。本课解决”怎么用看到的东西下判断”。 你完全没接触过 nDPI，所以本课从”如果没有 nDPI，你会怎么设计一个识别引擎”开始，一步步把它推导出来。

0. 把问题形式化（30 秒说清）

输入：一个观测（一个包、一条流、或一组流）。 输出：一个标签（应用/协议/服务类别）+ 一个置信度。

形式化：找一个函数

f: 观测 O  →  (应用 a, 置信度 c)

判定它好不好，只有三条（和第一课 A6 呼应）：

  1. 准确：在”没见过的流量”上也对（不是只在训练集上对）。
  2. 可算：在你这个观测点上算得出来（加密/ECH 之后还算得出吗）。
  3. 可维护：新 App 出现时，加一行规则还是重训模型？

整部”流量识别史”就是这三条之间不断妥协的历史。

注意 L3 的位置：nDPI 不是纯 DPI。它是”有状态的、多证据融合的协议识别框架”， 这是它能在加密时代活下来的根本原因。

2. L1 端口法：为什么当年够用，现在不行

2.1 原理

端口就是”服务的门牌号”：

端口服务依据
80HTTPRFC 9110 / IANA
443HTTPSIANA
53DNSRFC 1035
22SSHIANA
25/587SMTPRFC 5321
5222XMPPRFC 6120
5228/5229/5230Google GCM/FCM 推送Google 文档
1900SSDPUPnP 规范
5353mDNSRFC 6762

优点：零成本、可解释、对加密完全免疫。 缺点：它假设”应用 = 端口”，而这个假设在 2005 年前后就崩了。

2.2 为什么崩了

  1. HTTP 隧道化：一切都能塞进 80/443。
  2. P2P 故意随机端口：BitTorrent 早期就是随机挑端口。
  3. 移动 App 的服务器端口：大量业务走 443，十个 App 全用 443。
  4. CDN 与云：同一个 IP:443 背后是几百个不同服务。
  5. 端口复用：一条 443 连接里多路复用多个域名（HTTP/2 的 connection coalescing）。

文献：Moore & Papagiannaki, Toward the Accurate Identification of Network Applications（PAM 2005）系统性地指出——用端口做”标准答案”会系统性高估分类精度，因为很多流量落在未注册端口上，而把端口当作真值的评估方法本身就错。 Karagiannis et al., BLINC: Multilevel Traffic Classification in the Dark（SIGCOMM 2005）进一步证明：P2P 类应用会刻意使用非标准端口，端口法对它们几乎无效。

2.3 你的数据里的铁证

  • 443 端口上有 10 个 App 全都在（whatsapp 23.8%、reddit 13.3%、twitter 10.7%…）。
  • 端口分布的第一名是 1900（SSDP），占 22.9%——它根本不是任何 App。
  • 第二名 53（DNS）占 20.6%——也不是 App。

结论：端口能告诉你”这是 TLS/这是 DNS/这是局域网发现”，不能告诉你”这是哪个 App”。 在 nDPI 里，端口的作用被降级为”初始提示（hint）“，不是最终答案。

3. L2 载荷匹配（DPI）：原理、算法、死穴

3.1 什么是 DPI

Deep Packet Inspection = 不只读头部，还读载荷内容，在字节流里找”特征串”。

经典例子：

协议特征字节（偏移处）说明
HTTP 请求GET / POST / HTTP/1.明文方法名
DNS头部 flags + QNAME 格式结构化
TLS16 03 01/03 + 01（ClientHello）记录头 + 握手类型
SSHSSH-2.0-版本串
BitTorrentBitTorrent protocol握手 magic
SMB\xffSMBmagic

3.2 工程上怎么做得快：多模式匹配

不是”每次拿几十条正则去扫”，而是：

  1. Aho–Corasick 自动机（Aho & Corasick, Efficient String Matching, CACM 1975）： 把所有特征串构造成一个有限状态机，一次扫描同时匹配全部模式，复杂度 O(n)。
  2. 特征码布局：按”偏移 + 长度 + 内容”三元组描述，避免全文扫描。
  3. 流重组：TCP 分段要把载荷按 SEQ 拼起来才能匹配（这本身很贵）。

3.3 DPI 的三个死穴

死穴原因后果
加密载荷是密文特征串消失
规避（evasion）攻击者故意分片/重叠/乱序让 IDS 与主机看到不同字节经典文献：Ptacek & Newsham, Insertion, Evasion, and Denial of Service: Eluding Network Intrusion Detection (1998)
状态成本要重组流、要维持百万级流表高带宽下内存/CPU 爆炸

所以”纯 DPI”在 2015 年之后就不够用了。 这就是 nDPI 出现的背景。

4. L3 nDPI：一个”多证据融合”的识别框架（重点）

4.1 它是什么

  • 全称：nDPI（“n” 来自 ntop，Luca Deri 的公司/社区）。
  • 血统：OpenDPI（2008 左右停滞）→ nDPI（2011 起由 ntop 维护）。nDPI 保留了 OpenDPI 的协议识别思路，但重写并大幅扩展。
  • 形态：一个 C 库（LGPLv3），不是独立软件。它被嵌进 ntopng（流量监控）、nProbe（NetFlow 探针）、PF_RING（高速抓包）等。
  • 规模：支持数百种协议（随版本增长），并可扩展自定义规则。
  • 权威出处：Deri, Martinelli, Bujlow, Cardigliano, nDPI: Open-Source High-Speed Deep Packet Inspection, ISWCS 2014；以及 ntop 官方 GitHub ntop/nDPI。

一句话定位：nDPI 是一个逐包喂入、按流维护状态、多轮次缩小候选集的协议识别引擎，输出”主协议 + 应用协议 + 类别 + 置信度”。

4.2 架构：数据是怎么流过去的

        抓包 (libpcap/PF_RING)

这个架构的关键设计思想：

证据分级。强证据（解析出了 SNI 并命中主机名库）压过弱证据（端口像 443）。 每一层都可以”否决”上一层：端口说是 HTTP，但内容不是 → 改判。

4.3 输出字段的命名法：为什么叫 TLS.WhatsApp

nDPI 的输出是两级的：

ndpi_protocol {
    master_protocol : 承载协议（TLS / QUIC / DNS / HTTP …）
    app_protocol    : 承载之上的应用（WhatsApp / Reddit / YouTube …）
    category        : 类别（SocialNetwork / Chat / Media …）
    confidence      : 这个判断有多可靠
}

所以 TLS.WhatsApp 读作：“在 TLS 之上识别出 WhatsApp”。 而单独一个 TLS 读作：“确认这是 TLS，但看不出里面是谁”。

你的数据里的实际例子：

application_name含义流数
SSDP主协议就是 SSDP5,753
TLS是 TLS，但应用未知2,383
TLS.RedditTLS 之上是 Reddit808
TLS.WhatsAppTLS 之上是 WhatsApp730
QUIC.FbookReelStoryQUIC 之上是 Facebook Reel497
DNS.InstagramDNS 查询的目标属于 Instagram465
TelegramnDPI 有 Telegram 的专用检测器（不走标准 TLS）282

注意 DNS.Instagram 这种：nDPI 连 DNS 查询的域名都拿来归因。 这在取证上很有用（“这台设备在解析 instagram 的域名”），但它不等于”用户在用 Instagram”。

4.4 置信度（confidence）与”猜的”（is_guessed）

nDPI 的 confidence 是一个枚举，语义是”这个结论是怎么得出的”，从强到弱大致是：

强 ── 内容/结构解析命中（DPI）                        ← 最可信
   ── 缓存命中（之前已解析过同一主机/同一条流）
   ── 端口匹配（MATCH_BY_PORT）                       ← 弱
   ── IP 匹配（MATCH_BY_IP，来自 DNS 缓存）
弱 ── IP+端口匹配（MATCH_BY_IP_PORT）                  ← 最弱
   ── 未知（UNKNOWN）

⚠️ 具体整数编码随 nDPI 版本变化。要精确对照，请查你自己那份 nDPI 的 ndpi_typedefs.h 里的 ndpi_confidence_t 枚举。这是一个必须养成的习惯：不要凭记忆解释枚举值。

你的数据的实测：

application_confidence流数占比

application_is_guessed = 1 只有 535 条（2.1%），且集中在 confidence=1（498 条）。

这两列合起来告诉你一件大事：

91.5% 的流用的是同一个置信度取值，说明这份数据里 nDPI 的判定几乎全部来自同一种证据（很可能是”IP/缓存”这一类，而不是逐字节的深度解析）。 这正好解释了为什么我后面的实验发现：DPI 的判定能力 ≈ SNI 的判定能力（加 DPI 只比加 SNI 多 1 个百分点）。 因为当 SNI 可见时，nDPI 能做的最强的事也就是读 SNI。

4.5 nDPI 的局限（必须知道，否则会误用）

局限具体表现你的数据里的例子
粒度是”协议/服务”，不是”App 会话”一个 App 会同时产生几十种 DPI 标签whatsapp 的流有 70 种 application_name（SSDP/DNS/MDNS/TLS/TLS.WhatsApp/…）
加密后只能靠旁路TLS1.3 证书加密，ECH 会藏 SNITLS（无应用）占 2,383 条
共享基础设施会误判graph.facebook.com 出现在 10 个 App 里纯度仅 0.31
CDN 让 IP 信息失效同一 CDN IP 承载多个域名大量 amazonaws/cloudfront/googleusercontent
规则需要人工维护新 App 要加主机名/IP 列表版本更新成本
不做”用户行为”判断它说”这条流是 WhatsApp 协议”，不说”用户在聊天”—

4.6 为什么它仍然是最实用的方案

因为它是唯一同时满足”准确 + 可算 + 可维护”三条件的方案：

  • 它把”强证据优先”做成了架构（不是规则堆砌）；
  • 它对加密做了退让（承认只能靠 SNI/证书/IP 缓存），但没有放弃；
  • 它可扩展（自定义协议、自定义主机名列表）。

工程建议：如果你要做取证工具，不要自己重写 DPI，直接用 nDPI； 但必须自己再叠一层”App 归属”逻辑，因为 nDPI 的粒度是协议不是 App。

5. L4 统计/行为法：不看内容，看”形状”

5.1 核心思想

即使载荷全加密、地址全隐藏，“形状”仍然泄露身份：

  • 一次请求要几个包？
  • 双向比例多少？
  • 间隔是固定周期还是突发？
  • 有没有出现满载包？

经典工作：Karagiannis et al., BLINC（SIGCOMM 2005）提出三个层次：** ① 社会层（谁跟谁通信）② 功能层（这个主机扮演什么角色）③ 应用层（具体什么应用）**。 它完全不看载荷，只用流的图结构 + 统计特征。

机器学习路线：Moore & Zuev（SIGMETRICS 2005）用朴素贝叶斯 + 248 个流特征； Nguyen & Armitage（A survey of techniques for internet traffic classification using machine learning, IEEE Comm. Surveys & Tutorials, 2008）是这一路的权威综述。

5.2 这条路的两个硬约束

  1. 需要标注数据，而标注本身很贵（本数据集就是用”当时前台是哪个 App”当标签，所以才有 39.2% 的噪声）。
  2. 会漂移：App 改版、网络变化、设备换代 → 模型失效。 你数据里 day5 的分布与 day1–4 差异巨大，跨天准确率从 0.70 掉到 0.47，就是漂移的实证。

6. L5 指纹法：加密时代的”指纹学”

JA3 / JA3SClientHello / ServerHello 字段拼接 → MD5TLS 客户端库/服务端软件论文：Althouse et al. 2017
JA4 / JA4S / JA4HJA3 的可读化重构（含 ALPN、扩展数）同上，但更细更可读你的 client_fingerprint 就是 JA4
证书指纹证书链的 CN/SAN/签发者/公钥哈希服务端是谁（TLS≤1.2 可见）你的 server_fingerprint

关键认知（第一课已讲，这里再强调）：

指纹识别的是”实现”，不是”应用”。 十个 Android App 共用系统 TLS 库 → 同一个 JA4。 所以”JA4 指纹化 App”这个流行说法，在这份数据上是错的（实测纯度 0.33–0.51，覆盖 10/10 个 App）。

7. 回到你的数据：三条方法论结论

7.1 结论一：DPI 的增益几乎全部来自 SNI

特征视图APP_NDNS 准确率（5 折 IID）
V1 纯流统计0.701
V3 +TLS 元数据存在性0.739
V4a +SNI 明文0.765
V5 +nDPI 判定（oracle）0.775

从 V4a 到 V5 只涨 1.0 个百分点。也就是说：一旦你能读 SNI，nDPI 几乎给不出额外信息。 这与 4.4 节”91.5% 的流是同一个弱置信度”的观察完全自洽。

7.2 结论二：字段名 ≠ 字段语义（一个必须现场纠正的坑）

NFStream 的列 requested_server_name 文档里说是 SNI。但打开值看一眼：

值数量它其实是
mmg.whatsapp.net733✅ 真 SNI
239.255.255.2505,752❌ SSDP 组播地址（不是域名！）
_spotify-connect._tcp.local1,288❌ mDNS 服务名
xboxone / wpad / desktop-h7kp9hq各 30–50❌ NetBIOS/mDNS 主机名

统计：非空 20,727 条（82.5%）中，

  • 像合法域名的只有 14,470 条（57.6%）
  • IP 字面量 5,752 条（22.9%）
  • 其余是 mDNS/NetBIOS 主机名

教训：任何”明文元数据”列，第一件事是验证取值是否合法（域名长什么样？IP 长什么样？）。 如果直接拿 notna() 当 has_sni，你会把 5,752 条 SSDP 广播当成”有 SNI 的 TLS 流”。 我前面报告里用的 has_sni 就受此影响（偏大）；正确的做法是先做正则校验再判定。 这不影响”SNI 加权纯度 0.802 / 0.708”这类结论（那些是按具体域名算的），但会影响任何以 has_sni 为条件的规则。

7.3 结论三：识别链条应该是分层的，不是单点的

第 0 层：这是不是背景流量？        （SSDP/mDNS/DNS/IGMP → 直接丢弃，占 39.2%）
   ↓
第 1 层：这条流的主协议是什么？      （nDPI 的 master_protocol：TLS/QUIC/DNS）
   ↓
第 2 层：如果 TLS，能读到 SNI 吗？   （能 → 查"专属域名表"）
   ↓
第 3 层：SNI 共享怎么办？           （→ 退到统计特征：包长/方向/节奏）
   ↓
第 4 层：单流拿不准怎么办？         （→ 按目的 IP 聚合多条流投票）
   ↓
第 5 层：给出置信度 + 可读依据       （→ 就是第四课的规则）

这个分层就是”从第一性原理设计一个识别系统”的答案： 每一层只解决一个信息粒度的问题，上一层的信息不足时才下探。 nDPI 是第 1–2 层的优秀实现，但它不负责第 0/3/4/5 层——那正是你要补的。

ground truth真值用来评估的”标准答案”（本数据集最弱的一环）

9. 常见误解（自检）

误解事实
“nDPI 是防火墙”不是，它是一个库，只做识别不做阻断
“有 DPI 就能看穿加密”不能。它读的是握手明文和旁路信息
“端口 443 就是 HTTPS 网页”可能是 QUIC、可能是任何 App 的 API
“JA3 能识别 App”它识别 TLS 实现；同 OS 同库的 App 共享指纹
“DPI 分类器 = App 分类器”nDPI 给的是协议/服务，一个 App 会产生几十种标签
“流量分析 = 机器学习”不是。规则 + 分层 + 聚合往往比模型更有效（本任务里聚合 +54%，换模型 +3%）

10. 本课小结

  1. 端口法在移动 App 时代失效：443 上十个 App 全在，第一名端口是 SSDP。
  2. 纯 DPI 在加密时代失效：载荷是密文。
  3. nDPI = 有状态的、多证据分级的协议识别框架：端口只是提示，真正靠解析握手 + 主机名库 + IP 缓存。
  4. 它的输出是 master.app + category + confidence，粒度是协议/服务，不是 App。
  5. 它的能力上限被”能看到多少明文”决定；在看到 SNI 之后，nDPI 的边际贡献只有 1 个百分点。
  6. 想做 App 归属，必须在 nDPI 之上自己补：背景过滤 → 专属域名 → 统计兜底 → 多流聚合 → 置信度。
