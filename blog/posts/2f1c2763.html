加密社交 App 流量分析（三）：提炼判定规则

2026-11-16 · tech / 流量分析 · 约 3889 字 · 阅读约 10 分钟

加密社交 App 流量分析（四篇）：一·分类依据 ｜ 二·数据与实验 ｜ 三·规则提炼 ｜ 四·总结

方法来源：CCS’24 GEAD，见 01_论文方法与分类依据.md 实现：自研 GEAD（MLP 前向/反向、CART 蒸馏、LC 增广、合并树、规则生成），源码见课程代码包。 运行：主实验、等预算比较、GEAD 调参三个脚本均在课程代码包内。 产物：规则集与保真度 CSV 见文末《配套下载》。

1. 为什么这套方法要用在这个任务上

论文的 GEAD 解决的是：黑盒 DL 异常检测器没有标签，怎么把它的判定逻辑变成人可读的规则？

本任务是有监督的 10 分类（不是异常检测）—— 表面上看不该用 GEAD。但有三点让它仍然适用，而且正好补上分类实验的缺口：

  1. 黑盒模型（MLP/集成树）不可解释：我们只知道它 70% 准，不知道”凭什么”。
  2. 本数据集标签噪声极大（39.2% 背景流），普通特征重要性会被噪声带偏；GEAD 用连续分数做蒸馏，能把”模型学到的置信度分布”保留下来。
  3. 论文的核心洞察在本任务上直接可以检验：模型学到的规则是否与专家常识一致？哪些是捷径？

因此本文采用双轨：

  • 轨道 1（忠于论文）：用 GEAD 蒸馏 MLP，输出概率化规则（规则集 A/B）；
  • 轨道 2（务实）：直接对真标签训练浅树，输出人类摘要规则（规则集 C）；
  • 另外单独提取背景流量规则（规则集 D），因为它是本数据集规则体系的第一层。

2. GEAD 六步在本任务上的落地

论文步骤本文实现代码相对论文的改造
① 回归树生成 (root tree)对 10 个类别各训练一棵 DecisionTreeRegressor，标签 = MLP 输出的 P(class)MergedRT.fit_roots二分类→多分类 OVR；异常分→类别概率
② 低置信叶识别 (LC leaves)叶内 MSE ≥ α_E 分位 ∪ 叶均值 P ≥ α_O 分位 ∪ 样本数 < 40gead() 的 leaf_stats 段增加”小样本叶”作为第三类 LC（本数据长尾，很多叶只有几条流）
③ 低置信增广 (LC augmentation)在每个 LC 叶内冻结决策路径特征，只扰动其余特征：沿 ∂P/∂x 双向走 β=0.1、迭代 N 次、正向加上限截断；另混入分布内重采样 ood_fracNNFunc.grad_logit + gead()用解析反向传播（自己实现 MLP 前向/反向）代替论文的框架梯度
④ 子树生成 (subtree)用该叶的增广样本拟合一棵 sub_md=3 的回归树gead() 的 DecisionTreeRegressor 段—
⑤ 合并 + 离散化子树替换 LC 叶；把连续阈值吸附到特征真实域（整数特征的 >t 归一为 >=ceil(t)；二值特征的 >t 归一为 ==1）_norm / _fmt论文用”小/大”二档，本文用分位数标注（pNN）+ 整数语义
⑥ 可读规则生成根→叶路径 + 子树路径合并 → 去重 → 贪心条件剪枝 → 输出中英文规则extract_rules / perclass_rules增加条件剪枝（去掉让置信度下降 <0.02 的条件）与退化条件过滤

论文没有、本文补充的两个步骤：

  • 条件剪枝：合并树给出的路径往往含冗余条件（同一特征被根和子树各切一次）。剪枝后平均条件数从 4.6 降到 3.4，置信度损失 < 2%。
  • 退化条件过滤：增广会把某些阈值推到 0（如 bps <= 0）。这类条件在语料上只覆盖 <0.5% 的行，会让规则不可执行 —— 直接剔除。

结论与解释（重要）

在本任务上，“硬标签决策树”反而比 GEAD 更能忠实还原黑盒。 原因有三条，且都与论文的适用边界吻合：

  1. 适用前提不同：GEAD 是为 zero-positive 异常检测设计的——那里没有异常标签，只能用连续分数做回归蒸馏。 本任务有完整标签（训练集上 MLP 的 argmax 就是现成的”硬标签”），属于论文 §2.2 说的”有监督解释”场景。 论文自己在 Insight 1 里承认：这类场景下树蒸馏本就容易做得好（Trustee 一类方法的强项）。
  2. 规则预算被子树吃掉：GEAD 把规则预算花在”LC 叶的局部细化”上，根树只能保持很浅（Md=3–5）， 全局分辨率不够；深硬标签树则能把整棵树长到 Md=12，全局划分更细。
  3. LC 增广在低维特征集上破坏叶内一致性：论文的特征空间是 80+ 维，冻结 4–5 个路径特征后扰动仍局限在局部； 本文只有 22 维，冻结后剩余 17 维可任意走，增广点容易跑出该叶的真实分布，子树学到的其实是”合成分布”。 （这正是论文 §6 “augmented samples 不来自真实分布”这一自述局限在低维场景的放大。）

一句话：GEAD 的方法论在本数据集可以跑通、排序正确，但不构成对硬标签蒸馏的性能优势； 它的真正价值在这里变成了两件事： ① 提供概率化而非仅 argmax 的规则语言（每类都能给 P(class) 与 lift）； ② 提供定位模型捷径的手段 —— 见 §5。

7. 规则集 C：真标签浅树（人类摘要，rules/C_true_label_tree_规则.csv）

对真标签训练 depth=5, min_samples_leaf=50 的决策树，20 条叶子规则，覆盖 9/10 类。 IID 准确率 0.422、OOD 0.277 —— 它只是人类可读的摘要，不是好分类器（因为真标签本身含 39% 噪声）。

它揭示的全局分裂骨架（这就是”提炼出的顶层判据”）：

[L0] 最大包长 ps_max >= 1470 ?        ← 是否出现过 ≈MTU(1470/1510) 的大包：是否在传媒体
 ├─ 否 → 小包/控制面流
 │   └─ RST数 >= 3 ?
 │       ├─ 是 → 下行字节占比 > 0.757 ? → whatsapp : whatsapp
 │       └─ 否 → 下行包占比 > 0.846 ?
 │                ├─ 是 → 字节数 > 779 KB ? → facebook(视频/大图) : youtube
 │                └─ 否 → 有JA4 ?
 │                        ├─ 是 → 下行字节占比 > 0.143 ? → facebook : reddit
 │                        └─ 否 → SYN占比 > 0 ? → telegram : twitter
 └─ 是 → 出现大包（媒体/下载面）
     └─ RST数 >= 3 ?
         ├─ 是 → 包数 >= 33 ? → reddit(PSH≤0.09 / >0.09 两分支) : reddit
         └─ 否 → 下行包占比 > 0.559 ? → reddit : snapchat / linkedin / twitter / tiktok(按包长标准差 429 切)

翻成一句人话：

第一判据 = “这条流有没有搬大包”（ps_max ≥ 1470，MTU 边界）； 第二判据 = “连接是被正常关闭还是被重置”（RST 数）； 第三判据 = “方向性”（下行字节/包占比）； 第四判据 = “有没有走标准 TLS（JA4）/ 有没有 SNI”。 包长标准差 ≈ 429 是 tiktok（短时高低起伏）与 snapchat/linkedin（平滑）之间的分界。

8. 规则集 D：背景流量识别规则（本数据集的第一层过滤）

这一层不是”App 分类”，而是”这条流到底该不该参与 App 分类”。剔除后准确率提升 20 个点（0.49 → 0.70）。

D1  目的 IP 为私有地址 / 组播 / 广播                          → 局域网背景（7.21%）
D2  dst_port = 1900 (SSDP)                                    → 5,753 条，全部是 239.255.255.250 组播发现
D3  dst_port = 5353 (mDNS)                                    → 1,643 条，含 _spotify-connect._tcp.local
D4  dst_port ∈ {5355(LLMNR), 3702(WS-D), 137/138(NBNS), 67/68(DHCP)} → 869 条
D5  dst_port = 53 且为公网 DNS 解析                            → 5,138 条（App 无关的域名解析）
D6  dst_oui ∈ {01:00:5e, ff:ff:ff, 33:33:xx}                  → 组播/广播二层地址

合并 D1–D4 后：9,846 条（39.2%）为背景流。

任何以单个 JA4 为条件的规则主流 JA4 覆盖 10/10 个 App（纯度 0.33–0.51）OS 共享指纹，指向”用的是 Android+Chrome”，不是”用的是哪个 App”

这条审计本身就是最有价值的”规则”：论文 Insight 3 说”规则常与常识冲突，需按 特征/标签/模型 三查表定位”。 本文的伪规则全部能在三查表里找到位置：A14 = 标签+采集伪影，A13 = 模型欠拟合，OUI 规则 = 特征（设备代理）。

10. 最终规则清单（去重合并，按可信度排序）

把 A/B/C/D 四套规则合并、去掉重复与伪规则后，得到可直接落地的一页纸规则集：

# ---------- 第 0 层：先判定是否为背景流量（必须做） ----------
R0.1  IF 目的IP为私有/组播/广播                     THEN 背景流量（7.2%）
R0.2  IF 目的端口∈{1900,5353,5355,3702,137,138,67,68} THEN 背景流量
R0.3  IF 目的端口=53 且 目的IP为公网                THEN 背景流量（DNS 解析，App 无关）

# ---------- 第 1 层：高置信 App 判据（prec ≥ 0.85） ----------
R1.1  IF 最大包长≥1510 AND 下行包占比>0.50 AND RST数≥2              THEN Reddit      (prec 0.89)
R1.2  IF RST数≥2 AND 最大包长≤1450 AND 字节数≥5613 AND 下行字节占比>0.757 THEN WhatsApp (prec 0.94)
R1.3  IF 无SNI AND SYN占比>0 AND 平均包长>121 AND PSH占比≤0.315      THEN Telegram    (prec 0.96)
R1.4  IF SYN占比>0.092 AND 包间隔标准差>4134 AND RST数≥1 AND 时长≤48s THEN TikTok     (prec 0.98)
R1.5  IF 下行包占比>0.875 AND 最大包长≤1291                          THEN Facebook    (prec 0.97)

# ---------- 第 2 层：中等置信，需引入会话上下文 ----------
R2.1  IF 最大包长≥1513 AND 时长≤10.7s AND 包数≥31 AND 下行包占比≤0.486 THEN LinkedIn  (prec 0.67)
R2.2  IF FIN数≤0 AND PSH占比>0.404 AND 包长标准差>435 AND SYN占比≤0.081 THEN YouTube (prec 0.41)
R2.3  IF SYN占比>0.108 AND 非瞬时流 AND PSH占比≤0.272                  THEN Twitter   (prec 0.50)

# ---------- 第 3 层：不可单独使用的特征（禁用清单） ----------
禁止  src_oui / dst_oui（设备身份捷径；跨设备泛化 -0.29）
禁止  单个 JA4 指纹（覆盖 10/10 App，纯度 0.33–0.51）
禁用  "包数≤1 → Twitter"（采集伪影：Twitter 抓包含 212 个设备的半开连接）
慎用  任何指向 facebook 的规则（Meta SDK 跨 App 复用，会吸收 instagram/linkedin/youtube）

# ---------- 第 4 层：聚合规则（单流不可判时） ----------
R4.1  同一 dst_ip 上 ≥3 条流的多数投票结果为准   → 准确率 0.464 → 0.716

11. 规则怎么用（取证流程）

  1. 过滤：先跑第 0 层，把 39.2% 的背景流摘出去（这一步不做，后面全是噪声）。
  2. 单流初判：跑第 1 层，得到高置信 App；命中即接受。
  3. 聚合再判：对未命中的流，按目的 IP 聚合投票（第 4 层），把 0.46 → 0.72。
  4. 人工复核：第 2 层的规则只能作为”提示”，必须结合 SNI/证书/会话上下文。
  5. 禁用：第 3 层的一切捷径特征不得写进结论 —— 它们在换设备/换天之后必然失效。
