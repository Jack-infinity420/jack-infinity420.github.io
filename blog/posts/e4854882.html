2. 数据质量：本数据集最大的问题不是加密，而是标签噪声

2.1 39.2% 的流根本不属于被标注的 App

Label 的含义是”这条流被捕获时，手机上正在使用的是哪个 App”。但一次抓包里混入了大量设备/网络背景流量：

背景流量类型目的端口流数说明
SSDP / UPnP 发现19005,753组播 239.255.255.250，与 App 无关
mDNS53531,643_spotify-connect._tcp.local 等
私有/自建服务20002787局域网内设备互访
LLMNR5355350Windows 名解析
WS-Discovery3702290打印机/摄像头发现
DHCP / NBNS67,68,137,138267—
组播/链路本地目的地址—7.21%目的 IP 非公网
合计判定为背景—9,846 (39.2%)目的 IP 非公网 或 目的端口属局域网服务

每个 App 的背景占比差异极大：facebook / reddit 只有 21.6%，而 snapchat 62%、telegram 57%、linkedin 56%。

→ 这直接对应论文 Insight 3：规则与常识冲突的第一大来源是 标签错误。 本文后续所有实验都同时报告两个子集：

  • ALL：全部 25,116 条（含背景噪声）
  • APP：只保留目的 IP 为公网的流（15,270 条，60.8%）
  • APP_NDNS：再剔除公网 DNS（目的端口 53）的流（10,132 条，40.3%）——最干净的语料

3.1 五个由弱到强的特征视图（分级泄漏设计）

视图内容维数现实含义
V1 纯流统计①②③ 只取数值统计，不含端口、协议号、IP45载荷全加密、且五元组被隐藏时仍可用的”纯行为指纹”
V2 +L4 身份+ protocol, src/dst_port, ip_version55网络中间点常规可见
V3 +TLS 元数据+ has_sni, sni_len, has_ja4, has_srvfp59只能看到”有没有 ClientHello 扩展”，看不到内容（ECH 场景）
V4a +SNI 明文 + OUI+ requested_server_name(哈希 one-hot) + src/dst_oui130传统 TLS1.2 无 ECH：SNI 明文可见
V4b +仅 OUIV3 + src/dst_oui81用于隔离”设备身份”的影响
V5 +DPI oracle+ NFStream/nDPI 的 application_name、category、confidence257泄漏参照：模拟”如果直接用 DPI 分类器能有多准”

Label、capture_file（文件名含 App 名）、id、时间戳一律不作为特征。

⚠️ 一处已知的字段语义偏差（后续教程中发现，见 08_教程_3_nDPI与流量识别.md §7.2）： 本文的 has_sni 用 requested_server_name.notna() 判定，但该字段在非 TLS 流里也会被填充—— 其中 5,752 条是 SSDP 组播地址 239.255.255.250、1,288 条是 mDNS 服务名。 严格的”合法域名 SNI”只有 14,470 条（57.6%）。 这不影响本章”SNI 加权纯度 / 共享域名”类结论（那些按具体域名计算）， 但会让任何以 has_sni 为条件的规则偏松。

4. 分类实验一：特征视图消融（回答”凭什么分类”）

5 折分层交叉验证，HistGradientBoosting，三个子集：

视图ALL 准确率APP 准确率APP_NDNS 准确率
V1 纯流统计0.49090.66330.7007
V2 +L4 身份0.50550.66420.7256
V3 +TLS 元数据0.51050.67700.7389
V4a +SNI+OUI0.55790.72360.7651
V5 +DPI oracle0.56920.74150.7754

macro-F1（APP_NDNS）：V1 0.645 → V2 0.677 → V3 0.692 → V4a 0.709 → V5 0.724

读法

  1. 只用加密流统计（V1）就有 70% 准确率 —— 说明纯行为指纹确实携带 App 信息（论文”流量表示粒度”的第一层成立）。
  2. 从 V1 → V2 → V3 只涨 4 个点（0.701→0.739），说明 端口/协议/Fingerprint 存在性 的边际贡献有限。
  3. V4a（SNI 明文）一次涨 2.6 个点，是最大的单步增量 —— SNI 才是真正的强信号。
  4. V5 只比 V4a 高 1 个点（0.765→0.775）：这说明 nDPI 的判定基本就是 SNI + 证书，一旦 SNI 可见，DPI oracle 就没有额外信息量了。这条结论直接支撑”加密流量指纹 = 旁路明文元数据”的判断。
  5. ALL 子集准确率只有 49%–57%：背景噪声把上限压掉了 20 个点。不去噪就没有分类可言。

结论：

  • 集成树（HGB / ET / RF）> 单棵 DT > MLP > 线性模型。线性模型只有 37%，说明特征与类别边界是强非线性的。
  • MLP（“黑盒”）并不比树模型强，这为后文”用树去蒸馏黑盒”提供了现实前提：目标模型本身就不复杂。
  • 加入 OUI 后所有模型一起涨 3–8 个点 —— 这个增益来源可疑，§6 专门审计。

6.1 设备留出（GroupKFold by src_mac）

视图IID 5 折未见设备（GroupKFold）保持率
V10.6810.43864%

结论：一旦换成训练时没见过的手机，准确率腰斩（0.73 → 0.44）。 也就是说，IID 场景下那 0.73 里有约 0.29 来自设备/会话身份，不是 App 行为本身。 这与论文 Insight 2（监督模型容易出现捷径学习）在方向上一致，但本任务因为是”有监督分类”，捷径确实存在，与论文”异常检测很少捷径学习”的结论形成对照。

6.2 OUI 是被哪一类设备撑起来的？

  • src_oui = f8:e4:3b 的 2,011 条流 100% 是 whatsapp；
  • dst_oui = 08:86:3b 98 条 100% 单一 App；c6:8e:71/c6:8e:96 纯度 0.93/0.86。

即：OUI 的增益来自极少数只出现在某一个 App 抓包里的设备，属于典型的捷径特征，不能作为判据。

6.3 SNI 与 JA4 的真实纯度

特征覆盖率加权纯度是否可作判据
requested_server_name（SNI）75.6% of APP0.802部分可用；共享基础设施会误判
client_fingerprint（JA4）50.5% of APP0.624不可单独作判据

共享 SNI（跨全部 10 个 App 出现）：graph.facebook.com（Meta SDK）、play-fe.googleapis.com / play.googleapis.com（Play 服务）、i.ytimg.com、connectivitycheck.gstatic.com、device-metrics-us-2.amazon.com。

JA4 的两面性（一个有意思的发现）：

JA4流数覆盖 App 数纯度

→ 主流的几个 JA4 是 Android/Chrome/Conscrypt 的系统级 TLS 栈指纹，被所有 App 共用（覆盖 10/10，纯度 0.33–0.51）； 只有 App 自带 TLS 栈（自研 SDK/自研协议）的指纹才是”私有”的（纯度 1.00）。 这条结论与”JA3/JA4 可以指纹化 App”的常见假设相反，对取证实践很重要： 拿 JA3/JA4 单独做 App 归属，会把 10 个 App 判成同一个。

6.4 论文 Insight 3 的三查表——本数据集的答案

论文归因本数据集是否命中证据
特征提取不准部分命中dst_port=0、0.0.0.0 源地址、伪造形如 x.x.1.187 的地址；11 个常量列；TCP 标志位与包长统计口径需回归原始 pcap 才可信
标签错误强命中（主因）39.2% 的流是背景协议流量；同一台设备跨 9–10 个 App（src_mac→Label 纯度 0.361）；day5 类别分布剧变
模型训练不当命中用 MLP 蒸馏时，模型会把”单包流 → Twitter”学成一条高置信规则（见 03_规则提炼.md §5.1），实为 Twitter 抓包里 212 个设备贡献的大量异常单包流（占比 15.3%，为 10 个 App 最高）

7. 分类实验四：时间外推（Day-5 = OOD）

训练 day1–4，测试 day5（表 T3，APP_NDNS 子集）：

视图LogRegDTMLPRFETHGB
B-V10.3230.4130.4040.4690.4900.470
B-V20.3140.3800.3710.4680.4820.451
B-V30.3430.3780.4120.4760.4910.478
B-V4（+OUI）0.6110.6750.6890.7380.7340.743

（ALL 子集更低：B-V1 HGB 仅 0.323）

结论

  1. 跨天之后，纯统计视图掉到 0.47–0.49（相对 IID 掉 22–25 个点），说明 App 的统计分布对”哪一天/哪批设备”高度敏感。
  2. 唯一稳住的是 B-V4（+OUI）的 0.743，但这是 §6 已证伪的捷径 —— 跨天用同一批设备，OUI 就等于身份标签。这个 0.743 不能当作泛化能力。
  3. 因此本数据集上可信的跨天 App 指纹准确率约 0.47–0.49（10 分类，随机基线 0.10，macro-F1 0.44）。

混淆矩阵（Day-5）

可解释的混淆结构（与”共享基础设施”完全吻合）：

  • facebook 是”吸收池”：instagram 33%、linkedin 30%、youtube 25% 都被判成 facebook —— 这四个 App 都走 Meta/Google 的登录与 SDK 域名。
  • snapchat ↔ reddit 互混（0.12 / 0.25）：两者都是”小图 + 短连接 + 高 RST”的形态。
  • whatsapp ↔ linkedin 互混（0.14 / 0.13）：都是长连接心跳 + 小包。
  • telegram（0.64）、tiktok（0.65）、reddit（0.68）、twitter（0.61） 基本可分 —— 它们有专属的协议形态（MTProto / 短连接高频 / 大量 RST / 单包流）。

8. 分类实验五：多流聚合（本数据集提分的唯一有效手段）

论文与本数据集的 README 都强调 multi-flow aggregation。两种聚合尝试：

聚合方式单元数中位流数/单元最佳准确率
session = (capture_file,src_ip)1,39520.386
burst = 30 秒窗口8,17310.306
burst（仅 APP_NDNS）2,12210.486
按 dst_ip 对同一目的服务的多条流投票（≥3 条流）116≥30.716

前两种聚合失败，原因是本数据集的 (capture_file, src_ip) 分组极度长尾（中位数只有 1–2 条流，2583 条流集中在 1 个分组里），聚合后每条样本几乎等于单流。

有效的聚合是”按目的服务归并”：把判定给同一 dst_ip 的多条流做多数投票， day5 测试集上 0.464 → 0.716（+25 个点，+54%）。

结论：单条流的 App 归属本质上是不确定的；证据必须按”服务会话”聚合成组。 这正好复现论文在 CDIPS/Kyoto 上的观察——单个样本的判定依据弱，需要上下文。

9. 本章结论

问题答案
用什么分类？流级统计（①②③）+ 明文元数据（④），SNI 是唯一强且可迁移的单项
不用明文能到多少？APP_NDNS / IID 70.1%，跨天 OOD 47–49%
用上 SNI 能到多少？76.5%（IID），但它已是 DPI oracle 的 96% 水平
最大障碍标签噪声（39.2% 背景流）+ 设备身份捷径
如何提分按目的服务的多流聚合（0.464 → 0.716）
哪些”强特征”不能用设备 OUI（捷径）、JA4 单指纹（OS 共享，跨 10 个 App）
