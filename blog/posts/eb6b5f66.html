网络流量入门（二）：92 个特征是怎么算出来的

2026-11-17 · tech / 流量分析 · 约 4740 字 · 阅读约 12 分钟

网络流量入门（五篇）：零·导览 ｜ 一·从比特到流 ｜ 二·92 个特征 ｜ 三·从端口法到 nDPI ｜ 四·动手实验

第一课讲了”流”这个抽象。本课讲这个抽象里的每一列，物理上是被什么东西决定的。 只要你能把一个特征”还原成一个网络行为”，你就再也不需要背特征表了。 配套图见文中插图；统计来自 10 个 App × 5 天共 25,116 条流。

0. 一条特征合格的标准：三个资格

新手最容易犯的错是”把 CSV 所有列丢给模型”。实际上一条特征要能用，必须同时满足：

资格含义反例（你数据里真实存在）
可观测在你的观测点上能算出来你在交换机镜像口看不到 ECH 之后的 SNI
有因果能被”某个应用/协议行为”唯一解释src_port 是内核随机数，没有因果
可迁移换设备/换天/换网络后仍然成立src_oui（设备厂商）在新设备上立刻失效

第三资格是本数据集上最致命的：src_oui 在 IID 测试里让准确率涨 8 个点， 但”留出没见过的设备”后全体掉到 0.44。一个特征只要能被”设备身份”解释，它就不是 App 指纹。

下面按”物理来源”分七组讲。每组的结构都是：定义 → 怎么算 → 为什么有判别力 → 陷阱。

1. 第一组：体量（packets / bytes / duration）

1.1 定义与算例

列定义为什么是这个值
bidirectional_packets两方向包数之和计数器
bidirectional_bytes两方向字节数之和计数器（通常按 IP 载荷计，不含 L2 头；不同工具口径不同！）
src2dst_* / dst2src_*按方向拆开同上
bidirectional_duration_ms最后一个包时间 − 第一个包时间时间差
src2dst_duration_ms该方向首包到末包只在一个方向发包时可能为 0

1.2 为什么这三个数”极度重尾”

你的 25,116 条流：

中位数p90p99最大
包数48311,609928,191
字节数84838,20112,646,3731,158,252,748
时长(ms)41779,3761,217,9201,799,997

这是网络流量的普遍规律：不是正态分布，而是重尾（heavy-tailed / long-tailed）。 经典文献：Paxson & Floyd, Wide-Area Traffic: The Failure of Poisson Modeling (IEEE/ACM ToN, 1995) 指出网络流量既不是泊松也不是自相似那么简单，而是在多个时间尺度上都呈现突发性；Thompson, Miller & Wilder, Wide-area Internet traffic patterns and characteristics (IEEE Network, 1997) 给出了包长双峰的实测证据。

这对建模的直接影响：

  • 必须取对数：log1p(bytes) 之后分布才接近可建模的形状。线性缩放会被 1 GB 的那一条流主导。
  • 用中位数而不是均值做”典型值”：均值会被极值拉飞。
  • 树模型为什么天然占优：树只看”大小关系”，对单调变换不敏感，所以不需要你手工 log。

1.3 陷阱：duration = 0 的 3,698 条流

14.7% 的流时长恰好是 0。原因：单个包的流，首包即末包；或者多包在同一毫秒内（本数据的 1 ms 精度不够）。 所以 duration == 0 不是”瞬时传输”，而是”观测精度不够”。 由此派生：pps = packets / (duration/1000 + ε) 在 duration=0 时会爆炸。 我在代码里的写法是 df["pps"] = df["packet"] / (df["dur_ms"]/1000 + 1e-9) —— 这会让 pps 达到 1e11 量级，属于数值伪影，需要 log1p 或截断。

方法论：任何”比率型”特征，分母为 0 时都要问一句”这个无穷大是什么意思”。答案永远是”没有意义”。

2. 第二组：包长统计（min_ps / mean_ps / stddev_ps / max_ps）

2.1 为什么包长有判别力（第一课已埋线）

包长 = 协议头固定开销 + 离散的载荷尺寸。所以：

观察反推的行为
max_ps ≥ 1470这条流传过满载数据（媒体/图片/文件）
max_ps ≤ 200只发过小包（信令/心跳/查询）
min_ps ≈ 60出现过纯 ACK（说明是双向的，对端在回 ACK）
stddev_ps 大大包小包混杂（典型：下载中夹 ACK）
stddev_ps 小且 max_ps 小全是同尺寸小包（典型：心跳）

你的数据里的尖峰（第一课的图）：

  • min_ps 众数：66（19.0%，带时间戳的 ACK）、212（16.0%，SSDP 响应）、60（12.6%，纯 ACK 补零）
  • max_ps 众数：212（16.0%）、1514（6.0%）、1446、1292、167（4.6%）

注意 212 和 167 这两个值——它们不是 App 流量，而是 SSDP/mDNS 的发现报文（第一课算过：167 = 14+20+8+125）。

2.3 陷阱：ps 的口径

你的 ps 最大值是 1514，说明它包含 14 字节以太网头（1500 + 14）。 如果换一个抓包点（比如 Linux any 接口用 SLL 头 16 字节，或者 pcap 用 -s 截断），所有包的尺寸会整体平移 2 字节或整体截断。

这是流量分析最容易翻车的地方：把 max_ps > 1500 写成硬规则，换个采集点就全错。 正确写法是相对量（比如”max_ps 达到本数据 p90”）或者只比大小关系（“这条流的 max 比 min 大 20 倍以上”）。

3. 第三组：到达间隔（piat = packet inter-arrival time）

3.1 定义

相邻两个包的时间差。bidirectional_*_piat_ms 是把两个方向的包混在一起排序后算间隔；src2dst_* 只算该方向内部。

  • min_piat：最小间隔（≈ 背靠背发包，通常 0）
  • mean_piat：平均间隔
  • stddev_piat：间隔的抖动
  • max_piat：最大空档（停顿时长）

3.2 为什么它是最”行为化”的一组特征

间隔反映的是”应用什么时候想说话”，这是应用逻辑的直接投影，几乎不可能被加密掩盖：

时间结构mean_piatstddev_piat典型应用形态
突发式（请求→一次拉完）小大打开 App 刷首页
流式（持续喂数据）中（≈RTT）中视频播放
心跳式（固定周期）大（秒级）小长连接保活（WhatsApp/Telegram）
轮询式（不规律）中大消息同步、埋点上报

你的数据里的证据（中位数）：

Appmean_piat解读
twitter11.4 ms极快 —— 大量短连接瞬间完成就断
linkedin14.2 ms同样偏快
facebook20.6 ms—

tiktok49.0 ms分片缓冲
telegram71.8 ms明显最慢 —— 长连接心跳 + MTProto 的节流

telegram 的 71.8 ms 是 10 个 App 中唯一超过 70 的，这正是后面规则里 无SNI 且 SYN占比>0 且 平均包长>121 且 PSH占比≤0.315 → Telegram（prec 0.96）的物理来源： 它的”慢 + 无 SNI”组合几乎独家。

3.3 陷阱：piat 受切流参数支配

你数据的 max_piat 上限恰好是 119,999 ms（= 120 s = idle timeout）。 也就是说：“最长空档”这个特征，量的不是应用，而是分析工具的设定。 任何超过 120 s 的停顿，都被切成了两条流，你永远看不到。

方法论：看到”某个特征的极值恰好是个整数”（120000、1800000、65535、255）， 第一反应应该是”这是某个人为设定的边界”，而不是”这是自然的极值”。

4. 第四组：TCP 标志位计数（8 个 × 3 个方向）

4.1 每个标志的物理语义（RFC 9293 §3.1）

标志全称什么时候置位你能反推出什么
SYNSynchronize建连（SYN、SYN-ACK 都置位）有 SYN = 有人发起过连接
ACKAcknowledgment除首个 SYN 外几乎恒置位基本无信息量（几乎 100%）
PSHPush告诉对方”立刻把数据交给应用”有应用层数据交互
FINFinish有序关闭连接被正常收尾
RSTReset强制中止被拒绝/被放弃/异常断开
URGUrgent紧急指针有效现代几乎不用，你数据里恒为 0
CWR/ECECongestion Window Reduced / ECN-Echo显式拥塞通知现代很少用，你数据里恒为 0

4.2 一个必须知道的坑：SYN 计数是”包”不是”连接”

你的数据：

统计比例
有 SYN 的流24.0%
syn_packets == 10.1%
syn_packets >= 224.0%

为什么 ==1 几乎不存在？ 因为一次正常握手会产生 2 个带 SYN 位的包（SYN 和 SYN-ACK）。 所以：

  • syn_packets == 2 → 一次干净握手
  • syn_packets == 1 → 只看到一个方向（抓包点在中途、或 SYN-ACK 被丢弃）
  • syn_packets >= 3 → SYN 重传，说明有丢包或对端没响应

这解释了为什么”单包流”里有很多是 SYN：半开连接（SYN 发出去没有任何回应）。 你数据里 24.0% 的流有 SYN，但只有 20.4% 有 FIN —— 差额就是”没正常关闭”的那批。

4.3 RST 是”应用性格”的强信号

RST > 0 的流占 14.9%。按 App 看中位数：

App中位 RST 数
reddit2
whatsapp1
其余 8 个0

为什么 Reddit 的 RST 特别多？ 它的客户端使用大量”发一个 GraphQL 请求就断”的短连接（gql-fed.reddit.com）， 并且会用 RST 主动放弃（不读完响应就关）。这是客户端实现风格，不是协议要求。

这就是”行为指纹”的本质：不是协议规定的，而是这个 App 的开发者怎么写的代码。 所以它跨天稳定（同一份代码），但换 App 版本可能失效。

4.4 PSH 的含义常被误解

PSH 不是”数据包标记”，而是”发送方请接收方立刻交付”。现代 TCP 栈几乎总是对应用写入的数据置 PSH，所以：

Apppsh_ratio 中位
whatsapp0.345
tiktok0.286
telegram0.231
reddit0.227

snapchat0.077
facebook / instagram / youtube0.000

facebook 的 psh_ratio 中位为 0 是因为它的中位流只有 2–4 个包且是纯 ACK/DNS，不是”Facebook 不用 PSH”。 这提醒你：中位数为 0 往往意味着”一半以上的流里这个事件从未发生”，而不是”这个值很小”。

requested_server_name 的加权纯度是 0.802（在 APP 子集里）。但注意：

第一课讲过原理。这里给实测结论：

JA4 字符串本身就是可读的（JA4 格式：<协议><版本><SNI标志><密码套件数><扩展数><ALPN>_<密码套件哈希>_<扩展哈希>）：

t 13 d 1516 h2 _ 8daaf6152771 _ d8a2da3f94cd
│ │  │  │ │  │   └ 密码套件列表的哈希
│ │  │  │ │  └─── ALPN = h2
│ │  │  │ └────── 16 个扩展
│ │  │  └──────── 15 个密码套件
│ │  └─────────── d = 有 SNI 且有域名（域名被替换成哈希）
│ └────────────── 13 = TLS 1.3

所以 t13d1516h2_... 的含义是”TLS1.3 + 15 个密码套件 + 16 个扩展 + 支持 h2”—— 它描述的是一个 TLS 库的版本（BoringSSL/Conscrypt），而不是一个应用。 10 个 Android App 大多共用系统 TLS 库，所以共享同一个 JA4 完全合理。

7.1 为什么 capture_file 是最危险的泄漏

facebook_day3.pcapng 这个文件名里就写着答案。任何包含”文件名”或”文件顺序”的特征， 都会让模型学成”第 3 个文件 → facebook”。这类泄漏在学术论文里叫 data leakage / label leakage。

检测方法：把某个特征的取值和标签做交叉表，如果某个取值只对应一个类别且样本量很大，八成是泄漏。 你的数据里：

8. 特征质量检查清单（贴墙上）

在把任何一列丢进模型之前，问这五句：

  1. 它在我这个观测点算得出来吗？（ECH/QUIC 之后 SNI 还能看到吗？）
  2. 它的极值是个整数吗？（120000、1800000、65535 → 人为边界，不是自然属性）
  3. 它的分母会为 0 吗？（pps、bps 在 duration=0 时爆炸）
  4. 它能被”设备/时间/文件名”解释吗？（能 → 是捷径，不是特征）
  5. 换个采集点它会不会整体平移？（ps 是否含 L2 头 → 会）

DPI 元数据application_name application_category_name application_is_guessed application_confidence4别人的结论，第三课讲
明文元数据requested_server_name client_fingerprint server_fingerprint user_agent content_type5最强也最坑
采集上下文capture_day capture_file2只能用来划分，不能当特征
合计92实际可用约 45–60（去常量、去 ID、去泄漏）

10. 本课小结

一句话：每个特征都是”某个网络行为”的投影，你的任务是把投影反推回行为。

你想知道该看哪组特征
这条流在搬多少东西？体量（log 后）
搬的是什么类型（文本/图片/视频）？bytes_per_pkt、stddev_ps、max_ps
它多久说一次话？mean_piat、stddev_piat
它是请求-响应还是持续传输？syn_ratio、psh_ratio、duration
谁在主导（下载还是上传）？dn_ratio、dn_pkt_ratio
它是不是被拒绝了？rst_packets、fin_packets
它访问的是谁？requested_server_name（专属域名才有用）

下一步：知道了”有什么可看”，第三课讲”怎么用这些信息判定它是什么应用”—— 也就是从端口法到 nDPI 的完整方法谱系。

自测：见 09_教程_4_动手实验与自测.md 第 8–14 题。
